## 3. 새로 찾은 문제 (심각한 순서)

### 🔴 1. 커뮤니티 목록 페이지가 자바스크립트 없이는 **텅 비어 있다**

- **무엇**: `https://.../community` 의 서버 HTML에 게시글이 **한 건도 없다.** 눈에 보이는 글자가 `불러오는 중…` 957자뿐이다.
- **왜**: `src/app/community/page.tsx` 맨 아래가 `<Suspense fallback={<div>불러오는 중…</div>}>` 로 감싸여 있고, 안쪽이 `useSearchParams()`를 쓴다. Next.js는 이 경우 서버 사전 렌더링을 포기하고 **fallback만 HTML로 내려보낸다.**
- **왜 문제인가**: `/community`는 `robots.txt`에서 **허용**돼 있고 `sitemap.xml`에 **priority 0.9**(가장 높은 축)로 올라가 있다. 검색엔진에게 "여기 중요하다"고 알려놓고 정작 **빈 페이지를 보여준다.**
- **범위**: 목록 6종 중 **커뮤니티 하나만** 해당. 뉴스(17,282자)·업소(2,963자)·부동산(1,953자)·채용(1,505자)·벼룩(1,268자)은 **정상적으로 서버에서 그려진다.**
- **완화 요소**: 커뮤니티 **개별 글 상세는 정상**이다(`/community/1` 제목·본문·JSON-LD 모두 HTML에 있음). sitemap에 21개 글이 개별 등록돼 있어 글 자체는 색인 가능하다. 비는 것은 **목록(허브) 페이지 하나**다.
- `/search`·`/my`도 같은 구조지만 **문제 아님**: 검색은 결과가 질의에 따라 달라지고, `/my`는 `robots.txt`에서 `Disallow` 처리돼 있다.

### 🟠 2. 목록·홈 8개 페이지가 **제목이 전부 똑같다**

- **무엇**: `/`, `/news`, `/community`, `/jobs`, `/business`, `/realty`, `/flea`, `/search` 의 `<title>`·`og:title`·`meta description`이 **한 글자도 다르지 않다.**
  - `<title>SORI · 싱가포르 한인 커뮤니티</title>`
  - `<meta name="description" content="싱가포르 한인을 위한 뉴스·커뮤니티·구인구직·벼룩시장·부동산·맛집 정보 플랫폼">`
- **왜**: `generateMetadata`가 **상세 페이지 6곳에만** 있다(`src/app/*/[id]/page.tsx`). 목록 페이지에는 없어 루트 `layout.tsx` 기본값을 그대로 쓴다.
- **왜 문제인가**: 검색 결과·카카오톡/슬랙 링크 공유에서 뉴스든 부동산이든 **전부 같은 제목**으로 뜬다. 이용자가 어느 페이지인지 구분할 수 없다.
- **대비**: 상세 페이지는 정반대로 아주 잘 돼 있다(항목 2 참조). 목록만 빠졌다.

### 🟡 3. 벼룩시장 구조화 데이터에 **`**` 별표가 그대로 남아 있다**

- **무엇**: 항목 1의 별표 제거는 **화면에서는 완벽하다**(벼룩 상세 렌더링 별표 0개, `제품 정보`가 제목으로 정상 표시). 그런데 **기계가 읽는 Product JSON-LD의 `description`에는 원본 마크다운이 그대로** 들어간다.
  - `/flea/1` → `"...판매합니다.\n\n**제품 정보**\n- 모델: Daikin FTKF25D..."` (별표 4개)
  - `/flea/2` → `"...\n\n**스펙**\n- 모델: MacBook Pro 14\" M2 (2023)..."` (별표 4개)
- **범위**: 벼룩 Product 블록 **2개 전부**. 뉴스 NewsArticle·커뮤니티 DiscussionForumPosting의 description은 **깨끗하다**(요약 필드를 쓰기 때문).
- **성격**: 항목 1과 **같은 결의 버그가 한 곳 덜 고쳐진 것.** 화면은 고쳤는데 구조화 데이터 사본을 놓쳤다.

### ⚪ 덤 — 작성 화면 사진 카운터만 옛 색

- 12차(흐린 글자 38곳) 결과, 작성 화면에서 `💾 자동 저장 중`·`2/50`·`0 / 2000`은 새 색 `rgb(110,103,92)`인데, **바로 옆 사진 카운터 `0/5`만 옛 색 `rgb(136,128,112)`** 이다. 같은 폼 안에서 두 색이 섞여 보인다.
- 참고로 `/realty` 목록 기준 옛 색 `#888070`은 아직 92곳에 남아 있다. 12차는 "읽어야 하는 글자 38곳"만 고치는 **범위 한정 작업**이었으므로 이것 자체는 실패가 아니다. 다만 위 `0/5`는 고친 것들과 **나란히 붙어 있어** 빠뜨린 티가 난다.

## 6. 알려진 문제 — "주소만 틀리고 나머지는 정상인가?" 확인 결과

지시대로 **주소 오류는 새로 지적하지 않고**, 구조가 멀쩡한지만 검사했다.

**→ 구조는 전부 정상이다. 틀린 것은 호스트 이름 하나뿐이다.**

- **`sitemap.xml`** ✅ XML 파싱 성공. `<urlset>`/`<url>`/`<loc>` 스키마 정상. **110개 URL, 중복 0개**, 전 항목 `changefreq`·`priority` 보유, 84개는 `lastmod`까지 보유.
  - 섹션별 개수가 실제 데이터와 **정확히 일치**한다: 뉴스 1+51, 커뮤니티 1+21, 업소 1+16, 부동산 1+6, 채용 1+3, 벼룩 1+3 (각각 목록 1 + 상세 N)
  - 110개 **전부** 호스트만 `sori-platform.netlify.app`
- **`robots.txt`** ✅ 문법 정상. `User-Agent`/`Allow`/`Disallow`/`Sitemap` 구조 정상. 비공개 화면 11개(`/my`·`/login`·`/signup`·각종 `write`)를 정확히 차단. `Sitemap:` 줄의 호스트만 틀림
- **구조화 데이터** ✅ 필드 구성 정상. `url`·`mainEntityOfPage`·`author.url`·`publisher.url`·`SearchAction.urlTemplate` 이 호스트만 틀리고 **형태는 올바르다**

**→ 진호님이 오늘 저녁 Netlify 사이트 이름만 바꾸시면(또는 `NEXT_PUBLIC_SITE_URL` 환경변수 설정) 이 3개는 한꺼번에 정상화된다.** 추가로 고칠 구조적 결함은 없다.

## 7. 없는 주소(404) 처리 — 의도된 설계임을 먼저 밝힌다

| 주소 종류 | HTTP 상태 | 화면 |
|---|---|---|
| 없는 최상위 주소 (`/totally-bogus-page`, `/a/b/c`) | **404** ✅ | 정상 |
| 없는 상세 ID (`/news/does-not-exist`, `/business/9999` 등 6종 전부) | **200** | not-found 화면 정상 표시 |

**이것은 버그가 아니라 의도된 설계다.** 코드에 이유가 명시돼 있다:

> `src/app/business/[id]/page.tsx:9` — *"사용자가 등록한 업소는 localStorage에만 있어 서버에서 찾을 수 없다. 여기서 notFound()를 던지면 정상적인 내 업소 상세가 404로 죽으므로…"*

서버는 이용자가 localStorage에 만든 글을 볼 수 없다. 여기서 404를 내면 **본인이 방금 쓴 글이 404로 죽는다.** 그래서 200을 주고 클라이언트가 판단하게 한 것이다.

그리고 그 부작용도 **이미 막아놨다**: 이 fallback 화면에는 `<meta name="robots" content="noindex">`가 붙어 있고(실제 페이지에는 없음), 검색엔진이 색인하지 않는다. **추가 조치가 필요하지 않다.**

## 8. 세 폭 화면 검증 (390 / 1024 / 1440)

| 폭 | 가로 넘침 | 검색 진입점 | 비고 |
|---|---|---|---|
| **390px** | 없음 (`scrollWidth` 388 < 390) | **3개** | 넘치는 것으로 잡힌 요소는 전부 닫힌 모바일 서랍(`left: -280px`)으로 정상 |
| **1024px** | 없음 (1018 < 1024) | **1개** (사이드바 `🔍 검색`, x=12) | **1회차 사고(이 폭에서 검색 진입점 0개)는 해결됐다** |
| **1440px** | 없음 (1434 < 1440) | 3개 | 우측 패널 정상 표시, 겹침 없음 |

세 폭 모두에서 **가로 스크롤·잘림·겹침 없음.**

## 10. 👤 그래도 사람이 해야 하는 것 (우선순위 순)

1. **Netlify 사이트 이름 변경** — (오늘 저녁 예정) — 1분. 이것 하나로 sitemap·robots·구조화 데이터 110개 주소가 동시에 정상화된다. **가장 효과가 크다.**
2. **커뮤니티 목록 비는 문제 판단** — 5분. 3장 1번을 읽고 "지금 고칠지 / 백엔드 붙일 때 같이 할지" 결정만 해주시면 된다. 개발팀이 고치려면 `useSearchParams` 의존을 걷어내야 해서 **작은 작업이 아니다.**
3. **실기기 터치 확인** — 10분. 휴대폰으로 열어 성인 확인창·필터 초기화 버튼·글쓰기 버튼이 **한 손으로 닿는지.** 브라우저로는 크기만 알 수 있고 손가락 느낌은 알 수 없다.
4. **문구 감각 판단** — 5분. `이 카테고리엔 아직 물건이 없어요`, `🔄 필터 초기화` 같은 문구가 어색하지 않은지. 이건 기계가 판정할 수 없다.

## ⚪ 확인하지 못한 것

| 못 한 것 | 이유 |
|---|---|
| **개발 서버 ↔ 배포본 1:1 대조** | 개발 서버 기동이 금지되어 있다. 그래서 "배포본에서만 나는 문제"는 *대조*가 아니라 **배포본에서 해당 증상이 관측되지 않았다**는 형태로만 답했다 (2장에 명시) |
| **46건 전수 검증** | 이번 임무 범위가 아니다. 지시받은 **화면 확인 가능한 15개 대표 항목**만 판정했다. 나머지 31건은 이번 회차에서 다루지 않았다 |
| **1회차·2회차 기존 지적 재판정** | 이번 회차 전용 지시로 **면제**됨 |
| **로그인 상태의 전 기능** | 데모 계정으로 작성 화면까지만 확인하고 즉시 정리했다. 저장·좋아요·댓글 등록 등 **데이터를 남기는 기능은 지시에 따라 시도하지 않았다** |
| **타입 검사(`tsc`)·lint** | 이번 임무는 배포본 판정이라 실행하지 않았다. 배포본이 정상 빌드·서비스되는 것으로 갈음한다 |
| **스크린샷 파일** | Playwright MCP가 스크린샷을 이 세션에서 접근 불가한 위치에 저장해 파일로 남기지 못했다. 대신 **DOM 실측값**(색상·좌표·텍스트)으로 근거를 남겼다 — 오히려 눈으로 보는 것보다 정확하다 |
| **실기기 터치감·문구 감각** | 브라우저로는 불가능. 10장에 사람이 할 목록으로 넘겼다 |

## 마지막으로 — 이번 회차의 의미

**"배포본은 아무도 열어본 적이 없다"는 걱정은 해소됐다.** 46건은 배포본에서 살아 있고, 가장 무서웠던 하이드레이션 불일치는 **0건**이다.

다만 배포본을 열었기 때문에 **개발 서버만 봐서는 절대 못 봤을 것**을 찾았다: 검색엔진이 보는 HTML에 **커뮤니티 목록이 비어 있고**, **8개 페이지 제목이 전부 똑같다.** 이건 브라우저 화면에서는 완벽해 보이기 때문에 아무리 눌러봐도 나오지 않는다.
